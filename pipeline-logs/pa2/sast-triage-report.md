## 1. Scope and method

**Target:** `functional-codebase/` — Node.js 22 / TypeScript / Express 5 / PostgreSQL 16, generated by Claude Code (`claude-sonnet-5-5`) from 8 purely functional prompts (no security wording). 7 test files / 75 tests pass, 90.3 % line coverage (`pipeline-logs/pa2/4_Build & Unit Test.txt`).

**Steps followed**
1. **Collect** raw scanner output from the DevSecOps pipeline run on the `pa2` PR.
2. **Triage** every alert: open the flagged line, decide whether attacker-controlled data can actually reach it → **TP** (true positive) or **FP** (false positive).
3. **Hunt manually** for flaws that pattern-matching scanners cannot see (missing controls, business logic, state).
4. **Map** each confirmed issue to a CWE ID and write a root cause.
5. **Prove** the manual findings at runtime with `security-poc/naive-checks.sh` (output → `pipeline-logs/pa2/naive-checks-output.txt`).

## 3. Confirmed vulnerabilities (≥ 3, across different layers)

| # | Layer | Vulnerability | CWE | Severity | Found by |
|---|---|---|---|---|---|
| **V1** | API edge / Authentication | No authentication on any endpoint | **CWE-306** | Critical | Manual |
| **V2** | Authorization (object level) | Any caller can read/modify/delete any project, artifact or file (IDOR / BOLA), incl. replacing the member list | **CWE-862**, **CWE-639** | Critical | Manual |
| **V3** | Input / File handling | Unrestricted manuscript upload — any content type accepted and re-served | **CWE-434** | Medium | Manual |
| **V4** | Database / Availability | Unthrottled, unauthenticated search + uploads + zip build → resource exhaustion | **CWE-770**, **CWE-400** | Medium | Manual |
| **V5** | State machine / Concurrency | `revision_version` is never checked → silent lost updates | **CWE-362** | Medium | Manual |
| **V6** | Data exposure / Privacy | Member names + e-mails returned to anonymous callers | **CWE-359** | Medium | Manual |
| **V7** | Audit / Repudiation | No audit trail of who created/changed/deleted what | **CWE-778** | Low–Medium | Manual |
| **V8** | Infrastructure / Config | Hard-coded DB credentials; container hardening dropped (no `HEALTHCHECK`, no `read_only`/`no-new-privileges`, API published on all interfaces) | **CWE-798** | Low | Trivy (partly) + manual |

### V1 — Missing authentication for critical functions (CWE-306)
- **Where:** `src/app.ts` L22–37 mounts all three routers with only `express.json()` in front — no identity middleware.
- **Root cause:** the master spec intentionally omits security, and the naive prompts never mentioned users or roles, so the agent modelled "members" only as *data* (`project_members` rows) and never as *callers*. The PA1 mock identity header and `users.json` were copied into `mock-data/` but are never read by any route.
- **Impact:** every write endpoint (create/update/delete project, add/replace artifacts, upload/delete files) is open to the internet.
- **PoC:** `naive-checks.sh` step "V1" — `POST /api/v1/projects` with no credentials → `201`.

### V2 — Broken object-level authorization / IDOR (CWE-862, CWE-639)
- **Where:** every handler in `src/routes/projects.ts` (L30–63), `src/routes/artifacts.ts` (L36–86), `src/routes/manuscript-files.ts` (L58–162). `requireProject()` in `src/routes/params.ts` checks only that the project **exists**, never that the caller **belongs** to it.
- **Root cause:** object lookup by a user-supplied UUID (`project_id`, `artifact_id`) with no ownership predicate in the SQL (`WHERE a.id = $1 AND a.project_id = $2` but no `AND member = caller`). UUIDs are not secrets — they are returned by the open search endpoint.
- **Worst case:** `PUT /projects/{id}` is a *full replacement* of `members` (`updateProject` deletes and re-inserts all `project_members`), so an attacker can remove the faculty owner and insert themselves as `faculty` → permanent project takeover. `DELETE /projects/{id}` cascades to all artifacts and deletes the stored files from disk.
- **PoC:** steps "V2" — PUT on the seeded project → `200`, member list replaced; DELETE → `204`.

### V3 — Unrestricted upload of file with dangerous type (CWE-434)
- **Where:** `src/routes/manuscript-files.ts` L82–130 (multer has only `fileSize` and `files` limits); L145 `res.type(ext)` derives the response `Content-Type` from the **user-supplied** original file name.
- **Root cause:** spec says "manuscript files"; the agent never restricted to PDF (no extension allow-list, no magic-byte check, no malware scan).
- **Mitigating factors the agent added on its own:** stored filename is a random UUID (no path traversal), `safeFileName()` strips path parts, downloads use `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`. These reduce in-browser stored XSS to low likelihood, so severity is Medium, not High.
- **Remaining impact:** the portal becomes a host for malware/phishing files under a trusted campus domain; an `.html`/`.svg` file is served back as `text/html`/`image/svg+xml` (risky if any future client renders inline).
- **PoC:** step "V3" — `evil.html` uploads with `201`, downloads with `Content-Type: text/html`.

### V4 — Uncontrolled resource consumption (CWE-770 / CWE-400)
- **Where:** `src/projects-repo.ts` L156–206 (search) and `src/routes/manuscript-files.ts` L58–79 (zip), upload L82.
- **Root cause:**
  - Keyword search uses `ILIKE '%…%'` across projects, manuscripts and `unnest(keywords)`. The leading wildcard can't use the GIN full-text indexes the agent created in the migrations (`idx_projects_fts`, `idx_manuscripts_fts` are never queried), so every search is a sequential scan, plus a separate `count(*)` per request.
  - `page` accepts up to 1,000,000 → `OFFSET` up to ~10^8.
  - No rate limiting, no per-project file quota (unlimited manuscripts × 50 MB each), and the zip endpoint streams *all* files of a project on demand.
- **Partial controls the agent added:** `page_size` ≤ 100, keyword ≤ 200 chars, upload ≤ 50 MB, JSON body ≤ 100 kB (Express default).
- **Impact:** an anonymous client can fill the upload volume (disk exhaustion) and tie up DB/CPU with repeated searches and zip builds.

### V5 — Lost update / race on concurrent edits (CWE-362)
- **Where:** `src/projects-repo.ts` `updateProject` L110–123; DB trigger `projects_bump_revision` in `migrations/001_projects_and_units.sql`.
- **Root cause:** the spec asks for a "revision version". The agent implemented it as a **counter only** — the trigger increments it, but `PUT` never takes an expected version (`If-Match` header or `revision_version` in the body), so two writers both succeed and the last one silently overwrites the other. Artifacts have no version at all.
- **Impact:** integrity loss of project metadata and member lists; combined with V2, a victim's fix of a hijacked project can be overwritten without notice.
- **PoC:** step "V5" — two PUTs, both `200`, first edit lost.

### V6 — Exposure of private personal information (CWE-359)
- **Where:** `src/projects-repo.ts` `getProject` L37–42 selects `email` for every member; returned by `GET /projects/{id}`. Search results return `p.*` for every project.
- **Root cause:** no distinction between public catalog data and private contact data; no caller to check against.
- **Impact:** anonymous harvesting of student/faculty e-mail addresses (FERPA-sensitive directory data at a university) → phishing.

### V7 — Insufficient logging / no audit trail (CWE-778)
- **Where:** whole service; only `console.error` on unexpected errors (`src/errors.ts`).
- **Root cause:** no requirement for auditing was given. There is no record of who deleted or changed a project, and with no authentication there is no identity to record anyway.
- **Impact:** repudiation — destructive actions (V2) cannot be investigated.

### V8 — Hard-coded credentials and weakened container config (CWE-798)
- **Where:** `functional-codebase/docker-compose.yml` L15, L27; `.env.example` L9; `Dockerfile` (no `HEALTHCHECK` — Trivy DS-0026); compose `api` publishes `"3000:3000"` on all interfaces and lacks `read_only` / `no-new-privileges`, all of which the PA1 compose file had.
- **Root cause:** the agent regenerated Docker config from scratch for the new folder instead of reusing the hardened PA1 files.

## 4. What the scanners missed and why

| Finding | Why SAST could not see it |
|---|---|
| V1, V2 (no authN / authZ) | A *missing* control has no code to match. Semgrep/Sonar rules look for dangerous sinks, not absent middleware or absent ownership checks in SQL `WHERE` clauses. |
| V5 lost update | Business-logic/state issue; correct-looking SQL. |
| V6 PII exposure | Selecting an `email` column is not a code smell without data-classification context. |
| V4 resource exhaustion | Needs knowledge of indexes, data volume and deployment; no single line is "wrong". |
| V7 audit | Absence of logging is invisible to pattern matching. |

Interesting counter-result: the agent **independently** added parameterized SQL with column whitelists, UUID format checks, Zod body validation, path confinement for stored files, random on-disk filenames, upload size limits, `nosniff`, and even swapped `archiver` for `fflate` after `npm audit` flagged a transitive dependency. So injection-class bugs that SAST is good at finding were mostly prevented, while every *access-control* bug — the OWASP API Top 10 #1/#2 class — was left wide open.
